# Living Fellows 0.21.7 — Scavenging and task execution

## Goal

Make every autonomous loot operation a visible, auditable transaction:

`select -> reserve -> approach -> settle -> animate -> commit -> verify -> resume`

An item must never move before the owned Loot action completes. A successful
operation must prove that the exact object left its source and entered the
chosen companion inventory or worn bag exactly once. Danger, a new order,
capacity changes, target removal, save/quit, and competing companions must all
leave the item in one valid location.

## Build 42 research

The installed 42.20.4 `ISInventoryTransferAction` is the behavioral reference:

- world-to-character transfer uses the `Loot` action and sets `stopOnWalk`;
- validity is rechecked against the source, destination, capacity, allowed-item
  rules, corpse existence, and item transaction state;
- the inventory mutation happens only in the completed action;
- source and destination are dirtied only after transfer;
- `ItemContainer.Remove(InventoryItem)` returns `void`, so success must be
  established by containment, not by the method result;
- `ItemContainer.AddItem(InventoryItem)` returns the stored item, while
  `hasRoomFor(character, item)` and the allowed-item APIs may reject a move.

The vanilla action also addresses the local loot UI through the actor's player
number. Living Fellows therefore retains its effect-free, actor-owned visual
action instead of invoking the complete player UI action on a non-local
`IsoPlayer`. The gameplay transaction mirrors the native ordering and performs
strict postcondition checks itself.

Authoritative references:

- installed game `media/lua/client/TimedActions/ISInventoryTransferAction.lua`;
- installed game `media/lua/client/TimedActions/ISTimedActionQueue.lua`;
- official `zombie.inventory.ItemContainer` Build 42 API documentation.

## Runtime contract

Each actor owns at most one transient scavenging task. The task records the
exact source container, owner, item object, item type/name, category, selected
destination, source kind, phase, timestamps, and cancellation reason.

1. **Select** scores a bounded set of containers and useful items.
2. **Reserve** gives one actor exclusive ownership of that container lease.
3. **Approach** retains the target while navigation moves into interaction
   range. It never selects a second item on an approach tick.
4. **Settle** cancels the retained navigation path and requires a short stable
   stationary interval.
5. **Animate** starts one verified `Loot` timed action. Ordinary decisions may
   not translate or restart movement while this pose is owned.
6. **Commit** revalidates danger, command serial, source membership, load policy,
   and destination capacity after the animation.
7. **Verify** removes from the source, adds to the selected destination, and
   proves both postconditions. A failed destination add is rolled back and the
   rollback is itself verified.
8. **Resume** releases reservations, invalidates the load audit, remembers the
   container signature, exposes a short-lived completion status, and lets the
   next decision run.

Survival may cancel during approach, settle, or animation. No inventory has
changed at those points. Once commit starts it is synchronous and may not be
interleaved with another decision.

## Container memory

Memory is actor-local and runtime-only. It stores a bounded signature of the
container contents plus the inspection result. An unchanged container with no
useful item receives a long cooldown; a successful source receives a short
cooldown; a changed signature becomes eligible immediately. Player-opened
containers remain excluded by the existing explicit ownership flag.

The legacy `SC_CompanionVisited` marker remains informational but is no longer
a permanent exclusion: taking one can of food must not hide every remaining
useful item from all companions forever.

## Destination and follow-up

Useful supplies prefer a worn container with room, chosen by capacity and
weight reduction. Bags or clothing that are themselves upgrades first enter the
root inventory so the logistics system can equip them safely. If no worn bag is
valid, the root inventory is used. The same exact destination is revalidated at
commit. A completed loot invalidates the logistics audit so the next logistics
decision may equip, consume, pack, or shed the new item.

## Observability

The roster and Overview expose approach, settle, loot, verification, success,
and failure using the item display name. Debug builds emit one bounded line per
phase transition and one receipt on success:

`[SurvivorCompanion][scavenge] actor=<id> phase=complete item=<type> destination=<kind> result=looted`

Failures include the phase, source kind, item type, and stable reason without
printing Java userdata or unbounded stack data.

## Required verification

- no mutation before visual completion;
- exact single transfer after completion;
- destination-add failure restores the exact item to the source;
- missing item and danger cancellation preserve inventories;
- a new command cancels without a late commit;
- full/load-policy rejection preserves the source;
- a worn bag with room receives role supplies and remains recursively visible;
- bag/clothing upgrades enter root inventory for later equip;
- two actors cannot own the same source concurrently;
- corpse loot follows the same transaction and danger gate;
- reset/save boundary drops only transient task state and cannot duplicate or
  delete the source item;
- unchanged unhelpful containers are not rescanned every decision tick, while a
  changed content signature makes them eligible;
- gameplay, core/native, UI, static, packaging, and live-sandbox gates remain
  green.

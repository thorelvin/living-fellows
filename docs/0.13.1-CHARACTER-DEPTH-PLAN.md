# Living Fellows 0.13.1 Character Depth Plan

## Decision

Build the next patch around four connected features:

1. a stable personality profile that changes bounded AI preferences;
2. one personal objective at a time;
3. a read-only relationship journal;
4. one persistent personal keepsake per companion.

The patch should make a fellow feel like a person without weakening the existing survival AI. Personality and objectives may alter soft utility scores, dialogue, and safe scavenging/downtime preferences. They must never override the hard overrun, rescue, path, infection, or native-action safety gates.

This is an additive Build 42.20.x patch. It should preserve 0.13.0 companions and `SC_SaveV1`, pass the complete headless suite, and remain labelled as awaiting playtest until it has been exercised in-game.

## Why this direction

Research on NPC teammates shows that players can form meaningful social interpretations of AI teammates, but that perceived autonomy and the balance between control and personhood matter. A companion should therefore have preferences and continuity, not merely grant bonuses or obey with random flavour text. The design also needs behavioural consistency: a stated personality that does not influence decisions would harm believability rather than improve it.

The implementation follows those findings conservatively:

- personality produces small, explainable differences inside the existing AI;
- objectives invite care but do not turn the companion into a quest dispenser;
- the journal explains what the simulation already knows instead of inventing a parallel story state;
- a keepsake gives continuity to inventory and loss without locking the player's inventory UI.

## Current 0.13.0 audit

### Reusable contracts

- `SCDecision.evaluate` is the single best place to apply top-level personality and objective utility modifiers.
- `SCCombat.assessOverrun` already has absolute overrun conditions (`immediate >= 3` or three occupied sectors) and a configurable risk threshold.
- `SCMedical.rescueViable` already refuses a rescue with at least two immediate attackers or no escape against multiple threats.
- `SCRelationship` already owns deterministic background, trust, bond, morale, stress, bounded semantic memories, reveals, care counters, and time together.
- `SCCommands.writeStable`, `SCRegistry.defaultState`, and `SCPersistence` provide one bounded, transactional state path.
- `SCUI` already has adaptive tab layout and a scrollable detail panel. A sixth Journal tab fits the existing contract.
- `SCEncounter`, `SCDowntime`, `SCNeeds`, `SCMedical`, `SCLogistics`, and `SCNativeActions` use bounded inventory searches and verified transfers/actions.

### Gaps that this patch must close

- The current `personality` string defaults to `steady` and does not affect AI utility.
- There is no objective lifecycle or objective history.
- `captureInventory` stores type, condition, favourite state, and firearm state, but not owned item metadata.
- `captureInventory` currently captures only the root inventory list. A keepsake placed inside a companion-owned bag needs a narrow nested-carried adapter or it could disappear on restore.
- A personal item needs explicit protection at automated selection sites: emergency clothing tears, medical consumption, food/water selection, crafting material selection, player-camp supply selection, and native work preparation.
- `SC.Identity.release` is currently `0.11.0` while both `mod.info` files report `0.13.0`. Phase zero must fix this and add a test that prevents another identity/version drift.

## Architecture

### Module boundaries

Add four focused client modules:

| Module | Owns | Must not own |
| --- | --- | --- |
| `SCPersonality.lua` | deterministic profile, archetype label, bounded utility modifiers, dialogue voice hints | memories, objective progression, native traits, direct actions |
| `SCObjectives.lua` | objective generation, reveal, progress, completion, history, small safe preference bonuses | world scanning, movement, item transfer, relationship UI |
| `SCPersonalItems.lua` | keepsake assignment, item markers, ownership checks, save adapter, automated-use protection | player inventory restrictions, general transfer hooks, world recovery scans |
| `SCJournal.lua` | immutable projection of background, relationship, objective, keepsake, and memory state | mutations, rewards, scanning, command handling |

Keep `SCRelationship.lua` authoritative for social variables and semantic memories. Keep `SCCommands.lua` as the transaction/persistence adapter. Do not move gameplay safety rules out of Combat, Medical, Navigation, Needs, or NativeActions.

### Load order

`SCPersistence` can remain defined before gameplay modules because its functions execute only after bootstrap has completed. After `SCGameplayUtil`, load in this order:

1. existing senses/navigation/combat/medical/encounter/logistics/needs/downtime;
2. `SCPersonality`;
3. `SCPersonalItems`;
4. `SCRelationship`;
5. `SCObjectives`;
6. `SCJournal`;
7. `SCCommands`, `SCDecision`, and `SCUI`.

All cross-module calls should be resolved at runtime through `SurvivorCompanion`, as the current modules already do. This avoids a new circular `require` chain.

## Persistent data model

Keep `saveSchema = 1` and `SC_SaveV1`; all new fields are additive and have deterministic defaults. Add feature-local version fields so an incompatible future character-depth change can be migrated independently.

```lua
state = {
    -- Existing blocks remain authoritative.
    order = { ... },
    group = "alpha",
    personality = {
        archetype = "caring",       -- existing field, now meaningful
        trust = 0,
        bond = 0,
        morale = 55,
        stress = 12,
        memories = { ... },
        background = { ... },
        care = { ... },
        reveals = { ... },
        timeTogetherMs = 0,
        profile = {
            version = 1,
            courage = 0,             -- 0..100
            caution = 0,
            compassion = 0,
            practicality = 0,
        },
    },
    objectives = {
        version = 1,
        serial = 0,
        active = { ... },            -- at most one
        history = { ... },           -- at most 8
        nextEligibleAt = 0,
    },
    possessions = {
        version = 1,
        keepsake = { ... },           -- exactly one stable record
    },
    downtime = { ... },
}
```

Only primitive values and bounded Lua tables may be persisted. Never store an actor, item, square, container, or Java object in these blocks. Do not add flat mod-data mirrors for objectives or possessions; their canonical nested state is enough.

Extend `SCCommands.copyCommandState` with bounded structural copies of `profile`, `objectives.active`, every objective-history row, and `possessions.keepsake`. This is required because conversation commands use a staged copy: revealing `plans` must not mutate the live state through a shared nested table before `writeStable` succeeds. The existing `stableEntryKeys` snapshot already includes the canonical `state` field and remains the rollback boundary.

### 0.13.0 normalization

On first load of an older record:

- derive the profile from the stable companion `sc-` ID and existing background;
- preserve all existing relationship values and memories unchanged;
- create an empty objective block, then generate an objective only after the actor is fully restored;
- create a keepsake record only after inventory restoration completes;
- write the normalized blocks through the existing stable transaction path.

The result must be deterministic and idempotent. Repeated normalization cannot generate a different profile, duplicate an item, duplicate a reward, or advance the objective serial.

### Carried keepsake persistence

Do not expand this patch into a rewrite of general nested-container persistence. Instead, add one narrow adapter for the one owned keepsake:

- root inventory entries continue through the normal `captureInventory` path and receive a bounded `personal` marker record;
- a second bounded recursive scan checks whether the marked keepsake is carried inside a companion-owned nested container;
- if it is nested, persist one `nestedCarried` item snapshot in `state.possessions.keepsake`, using the same safe item fields as normal inventory capture;
- if it is not anywhere in the companion inventory, persist status `not_carried` and no item snapshot;
- on restore, first restore normal inventory, collect any restored personal keys, and only recreate the nested snapshot at the root when its key was not already restored;
- restoring a previously saved carried item is persistence, not replacement. A genuinely absent/lost item must never be recreated;
- if duplicate copies with the same personal key are detected, retain one verified item, report a diagnostic, and do not silently keep both.

This preserves the personal item when the player puts it in the fellow's own bag without changing the save behaviour of unrelated nested inventory.

## Feature 1: personality that affects behaviour

### Profile

Generate four 0..100 dimensions from the stable companion ID, then select the highest dimension as the primary archetype:

- `brave`: courage-led;
- `cautious`: caution-led;
- `caring`: compassion-led;
- `practical`: practicality-led.

Use a versioned deterministic hash. Give the primary dimension a clear lead while retaining variation within an archetype. Existing 0.13.0 `steady` records should be normalized to the generated archetype rather than creating a fifth inert profile.

Do not map these dimensions onto vanilla player traits or mutate `IsoGameCharacter` traits. They are social/decision preferences owned by this mod, while vanilla traits remain engine state.

### Behaviour contract

`SCPersonality` should expose pure functions such as:

```lua
Personality.initialize(companionId, background, savedProfile)
Personality.adjustDecision(profile, candidate, context)
Personality.overrunThresholdDelta(profile, context)
Personality.adjustDowntime(profile, activity)
Personality.voice(profile)
```

Rules:

- Top-level candidate adjustment is capped at `-8..+8`.
- Combat overrun threshold adjustment is capped at `-4..+4`.
- Brave fellows may hold slightly longer when an escape route and support exist.
- Cautious fellows favour retreat/tactical movement indoors, at blind corners, and without a clear exit.
- Caring fellows favour treatment and rescue.
- Practical fellows favour repair, craft, useful work, and safe scavenging.
- Immediate medical self-preservation, downed state, explicit player retreat, immediate attacker counts, occupied-sector overrun, rescue viability, navigation viability, hold-fire, and infection/death rules remain absolute.

Apply the profile once per decision cycle, not through repeated `getModData()` calls. `SCCombat` may read the already-normalized command state passed to `assessOverrun`; it should not perform its own personality lookup.

### Consistent expression

Use the same primary archetype to select concise wording for `status`, `needs`, `opinion`, and objective conversations. Personality changes phrasing, not facts. A cautious fellow cannot claim an exit is unsafe if senses/navigation do not report that context, and a brave fellow cannot claim a rescue was attempted if no event exists.

## Feature 2: personal objectives

### Design rules

- Exactly one active objective per companion.
- Objectives are wishes, not mandatory quests: no time limit, no trust decay for ignoring them, no HUD spam, and no player XP or free high-value loot.
- A hidden objective becomes visible only through a new `plans` conversation after its reveal threshold is met. The Journal reflects that state but never changes it.
- A completed objective records one semantic memory and grants one small, non-repeatable morale/relationship response.
- A new objective becomes eligible after at least six in-game hours. It is generated only on the bounded objective cadence.
- Objectives may add at most `+12` to a matching safe item score, `+6` to matching downtime, and `+4` to top-level safe scavenge/downtime utility.
- They never expand scan radii, choose player-visited loot, bypass reservations, create unsafe detours, or override current orders.

### Initial objective catalogue

| Objective | Evidence for progress/completion | Safe influence |
| --- | --- | --- |
| `keep_medical_ready` | bounded inventory has two clean bandage-capable items | medicine scavenging preference |
| `find_something_to_read` | companion obtains eligible unread literature | literature preference; read downtime |
| `put_gear_in_order` | verified repair completes or primary weapon reaches the defined condition | repair downtime preference |
| `improve_shelter` | verified barricade `finish_work` fact while assigned to a stable work/guard area | build downtime preference only |
| `share_a_proper_meal` | existing relationship observer records a real meal after the objective is active | safe food preference only |
| `recover_keepsake` | the marked keepsake returns to the companion inventory | memento preference in unclaimed containers only |

Choose candidates using background and personality. Examples: carpenter/mechanic/practical favours gear or shelter; teacher/librarian favours reading; nurse/paramedic/caring favours medical readiness. Filter out objectives already satisfied and recently completed.

Do not claim that a companion has a “safe home” yet. The current mod has guard/work anchors but no authoritative base boundary or ownership model. `improve_shelter` is deliberately tied to one verified work result. A true home/base objective belongs in a later base-life patch.

### Lifecycle

```text
eligible -> hidden/active -> revealed/active -> satisfied -> history
                               |                 |
                               +---- no timer ---+
```

Each objective has a stable instance key (`companionId`, kind, serial), creation time, reveal state, normalized progress, and optional completion time. Completion must compare and commit the instance key atomically before applying a memory/reward. This prevents duplicate completion on reload or repeated observer pulses.

Progress should be mostly event-driven:

- `SCCommands.noteDowntime` forwards verified work facts;
- `SCRelationship.observe` forwards real meal/treatment events;
- keepsake inventory changes are checked by `SCPersonalItems`;
- simple inventory objectives are audited every 5 seconds with the existing item cap.

No new `Events.OnTick` hook is permitted.

Generate an initial hidden objective for every successfully initialized fellow, including a neutral encounter, so their behaviour and conversation have continuity before recruitment. Only recruited fellows are persisted under the existing rules. `Relationship.respond("plans")` should delegate reveal/response logic to `SCObjectives` using the already staged command-state copy.

## Feature 3: relationship journal

Add `journal` to `TAB_IDS`/`TAB_KEYS` and render it in the existing scrollable detail panel. `SCJournal.build` returns a bounded read model; opening or refreshing the tab must never reveal, reward, generate, or advance anything.

Sections:

1. **Who they are** — primary archetype and only the background facts already revealed.
2. **How they feel** — relationship tier, mood, and up to three evidence-based reasons.
3. **What they want** — revealed active objective and progress, or a reserved/unknown line.
4. **What they keep** — keepsake description and `carried`, `not carried`, or `missing/unknown` status after reveal.
5. **What we have been through** — at most the latest 12 semantic memories, newest first.
6. **Care and shared life** — bounded existing counters and time together.

Unrevealed background, objective, or keepsake fields must render as unknown—not leak their values in tooltips, accessibility text, command descriptions, or debug-free summaries. Objective reveal is owned by the staged `plans` conversation. Keepsake meaning/backstory is revealed through the existing staged background conversation once its trust gate is reached; merely opening the inventory or Journal does not mutate social state.

Add `plans` to the conversation action allowlist and an overview button labelled with a natural question such as “What are you hoping for?”. The response can reveal the active objective when trust permits, or state that the fellow is not ready to discuss it. It cannot generate a new objective on demand.

## Feature 4: personal keepsake

### Assignment

Each companion owns one persistent, low-value memento:

1. scan at most `maxInventoryItems` after new-spawn/recruit or successful restore;
2. prefer an existing native memento (`isMemento()` or verified memento tag);
3. if none exists, add and verify one `Base.Photo` at the root inventory;
4. mark it favourite as a UI hint;
5. put the authoritative ownership marker in the item's mod data.

Build 42.20.4's local item scripts define `Base.Photo`, `Base.Photo_VeryOld`, `Base.Locket`, and other items with the native memento tag. `Base.Photo` weighs 0.1 and has no survival advantage, making it the safest fallback.

Use exact primitive markers, for example:

```lua
item:getModData().SC_PersonalOwnerId = companionId
item:getModData().SC_PersonalKey = companionId .. ":keepsake:1"
item:getModData().SC_PersonalKind = "photo"
item:getModData().SC_PersonalVersion = 1
```

Do not use native `InventoryItem:getID()` as the persistent identity. Inventory restoration recreates items, so the runtime ID may change. Persist the mod-owned key beside the inventory entry and reapply its exact markers after `AddItem` succeeds.

### Player agency and automation protection

- The player may manually transfer, drop, unfavourite, store, or destroy the item. Do not hook or block the vanilla inventory UI.
- Favourite state is a hint; the owner marker is authoritative.
- Automated systems may read or repair a keepsake, but must not consume, tear, craft with, burn, donate, or assign it to another fellow.
- Add one shared `PersonalItems.isProtected(item, actor, operation)` predicate and use it during item selection in Medical, Needs, Downtime, Encounter camp-supply selection, Logistics/native work material selection, and future item consumers.
- Do not put the protection inside the generic low-level transfer helper; that would also interfere with legitimate transactional moves and possibly player-facing inventory operations.
- Do not scan the world for a lost item. If it leaves the companion's bounded inventory, the Journal reports “not carried” or “whereabouts unknown”. Returning the same marked item completes `recover_keepsake`.
- Never silently spawn a replacement after assignment. Loss should remain meaningful.
- A keepsake saved inside a companion-owned nested bag is restored once at the root because general nested inventory is not currently reconstructed. The Journal may explain that the fellow reorganized it; this must not be treated as a newly spawned replacement.

## Performance budget

- zero additional global tick hooks;
- personality adjustment: pure arithmetic once per decision cycle;
- objective audit: at most once per 5,000 ms per active fellow;
- at most one active objective and eight history entries per fellow;
- at most one keepsake and one inventory marker scan per objective audit/recruit/restore/save path, capped by `maxInventoryItems`;
- Journal projection only when the selected row is described/refreshed, with at most 12 displayed memories;
- no new square, building, room, container, zombie, or unloaded-world scan;
- existing scheduler soft frame budget and circuit breakers remain authoritative.

Add configuration values for objective cadence and caps, but do not expose tuning UI in this patch.

## Implementation sequence

### Phase 0 — baseline and identity guard

- Run all current core, gameplay, UI, bridge, packaging, and clean-room gates.
- Fix `SC.Identity.release` to match `modversion`.
- Add a static gate that compares root/versioned `mod.info`, namespace release, and release packaging version.

### Phase 1 — state and pure modules

- Add `SCPersonality`, `SCObjectives`, `SCPersonalItems`, and `SCJournal` with no runtime hooks.
- Extend registry normalization and command snapshot/write/export/restore without changing old relationship fields.
- Add deterministic/idempotent unit tests before behavioural integration.

### Phase 2 — persistence and keepsake safety

- Extend inventory entries with a bounded `personal` record containing only owner/key/kind/version.
- Add the single-item `nestedCarried` adapter and exact-key de-duplication; do not broaden the patch into general recursive container restoration.
- Restore item metadata only after verified native `AddItem`.
- Assign the initial keepsake after full actor/inventory initialization.
- Add the shared protection predicate to every automated consumer/selector and test rollback paths.

### Phase 3 — bounded behaviour

- Apply personality modifiers centrally in `SCDecision.evaluate`.
- Apply the capped threshold delta in `SCCombat.assessOverrun` while retaining all absolute overrun conditions.
- Apply practical/caring activity preferences after Downtime creates its normal candidates.
- Add objective item/activity bonuses inside existing safe scoring functions.
- Connect verified relationship, downtime, and keepsake events to objective progress.

### Phase 4 — conversation and journal UI

- Add the `plans` conversation.
- Add Journal tab/read model and all EN/NO translations.
- Verify six-tab layout, long Norwegian labels, 720p minimum bounds, wrapping, scrolling, selection changes, and dock/collapse behaviour.

### Phase 5 — verification and private candidate

- Run the complete test/build/installer/parity suite.
- Install a private 0.13.1 candidate without changing Workshop state.
- Mark the result “headless-ready, playtest required”. Do not call it released until a game session covers the playtest matrix below.

## Test matrix

### Personality

- Same companion ID/background always gives the same profile across reset/restore.
- Values are bounded and primary archetype has a deterministic lead.
- Brave and cautious profiles change soft scores monotonically within the cap.
- Both profiles still retreat on absolute overrun.
- Caring increases rescue priority but `rescueViable` still refuses two immediate attackers.
- Practical increases repair/craft preference but cannot start an invalid or unverified native action.
- Dialogue facts remain identical across voice variants.

### Objectives

- Older state normalizes exactly once.
- Unsatisfied objectives are not selected when already true.
- Hidden data does not leak through Journal or `Commands.describe`.
- Each verified event advances only matching active objectives.
- Completion memory/reward happens exactly once across repeated pulses and save/load.
- History stays at eight entries and candidate filtering prevents immediate repetition.
- No objective changes order, scan radius, reservation, or safety decisions.

### Keepsake

- Existing memento is preferred; otherwise exactly one verified `Base.Photo` is created.
- Marker and favourite state survive save/restore.
- A keepsake inside a companion-owned nested bag is restored exactly once; an absent/world-stored keepsake is not recreated.
- A recreated item keeps the mod-owned key even though native runtime identity changes.
- It is excluded from emergency tearing, medical/needs consumption, craft materials, camp supply, and another fellow's automated acquisition.
- Reading/repair may use it without consuming or changing ownership.
- Manual player transfer still works.
- Returning the marked item completes the matching objective once; an unrelated item of the same type does not.
- Failed `AddItem` or marker restoration aborts/rolls back without duplicating inventory.

### Journal/UI

- Journal construction is mutation-free and deterministic.
- Only revealed data appears.
- Timeline is capped and ordered newest first.
- Six tabs fit or wrap through the existing adaptive layout at 720p and with Norwegian strings.
- Content remains scrollable and preserves a clamped scroll position on refresh.
- EN/NO translation key sets are identical.

### Regression and gates

- Existing combat, rescue, Knox, navigation, door/window/stair, vehicle, needs, downtime, spawn, persistence, inventory, UI, and clean-room tests remain green.
- No extra `Events.OnTick` registration.
- No Java object enters persistent state.
- Source/payload/install hashes match after private install.
- Debug spawn remains source-off/install-on only for the private candidate; production release remains off.

## In-game acceptance matrix for the later playtest

The patch is not release-complete until one session verifies:

1. four generated fellows show stable but visibly different preferences without obviously suicidal behaviour;
2. rescue remains conservative under a swarm;
3. an objective reveals, progresses from a real action, and completes once;
4. Journal survives selection changes, save/reload, and long translated text;
5. a keepsake can be moved by the player, is not consumed by companion automation, and returns with its identity intact;
6. an old 0.13.0 fellow restores without duplicate items, duplicate memories, or changed relationship values;
7. no recurring errors, menu crashes, visible zombie animations, or measurable new stutter appear.

## Explicitly deferred

Defer these until the four-feature patch has been playtested:

- relationship penalties, grudges, refusal, or disobedience;
- bereavement, graves, memorials, or inheritance after death;
- fellow-to-fellow relationships and group social simulation;
- a formal base boundary, room ownership, or “safe home” simulation;
- autonomous cross-map objective travel or world searches for missing keepsakes;
- procedural free-form dialogue or external AI services;
- Workshop publication.

These are valuable future layers, but each adds new failure modes or simulation cost. The 0.13.1 state and module boundaries are deliberately designed so they can be added later without replacing this patch.

# Living Fellows 0.22.8 — Public Beta Reliability Pass

Status: implementation plan  
Target: Project Zomboid 42.20.4, single-player  
Baseline: Living Fellows 0.22.7

## Outcome

0.22.8 is a reliability release, not a feature release. Its purpose is to make
every companion action finish, cancel, recover, or fail visibly without leaving
the actor in a moving kneel, a stale path, an endless retry loop, an occupied
vehicle transaction, or an uncertain inventory state.

The central change is a small action-supervision layer. Existing subsystems keep
ownership of their gameplay transaction and side effects; the supervisor owns
arbitration, phase reporting, pre-emption rules, timeouts, bounded retries, and
the public read model. This avoids replacing working transactional code while
removing the present ambiguity over which subsystem controls the actor.

## Evidence from the current build

| Area | Current strength | Reliability gap to close |
| --- | --- | --- |
| Native actions | `SCNativeActions.activityStatus()` recognizes Living Fellows visuals, needs, work, and unknown native actions. It does not clear unknown vanilla or third-party actions. | It is a partial activity view, not a full coordinator. Downtime, medical, scavenging, logistics, base work, autonomy, decision work, and vehicles still keep independent transaction state and pre-emption logic. |
| Locomotion | `SCLocomotion` protects owned interaction poses from ordinary movement and records a debug movement history. | There is no single invariant proving that every non-locomotion owner has released the actor before movement resumes. Public reports do not retain enough action history to diagnose pose drift. |
| Medical downtime | `SCMedical.treat()` already has staged reservation, optional emergency cloth tearing, animation, commit, verification, and rollback. | `SCDowntime` separately selects and animates `replace_bandage`, then asks Medical to commit. It selects solely from `dirtyBandages > 0`, so a companion with no clean bandage can repeatedly start, be decision-pre-empted, and finish as the opaque `completion_failed`. This was reproduced in the local 0.22.7 console. |
| Scavenging | The 0.21.7 transaction already follows select → reserve → approach → settle → animate → commit → verify. It revalidates command serial, source membership, capacity, destination rules, and proves the exact item moved once. | The transaction is not registered in a common actor-wide owner view. Animation interruption, navigation terminal failure, capacity change, and repeated source failure are locally described but not consistently surfaced to the player or support report. |
| Logistics and equipment | Recursive bag audits, load policies, clothing/bag upgrades, verified wear transactions, surplus deposit/drop, and direct weapon-equip verification exist. | Logistics has another local transaction lifecycle. An accepted weapon command reports dispatch rather than the later verified result, and equipment failures are not part of one actor action history. |
| Navigation | The planner classifies actors, vehicles, doors, thumpables, moved objects, vegetation, stairs/slopes, continuous geometry, and world collisions; it blacklists failed edges and uses native telemetry. | After the configured three recovery attempts, the same goal is marked `stuck_terminal` until a materially different goal/action arrives. The terminal reason is not a clear player-facing state, and target-level failure memory cannot yet select a different semantic interaction point or controlled fallback. |
| Vehicles | Seat manifests, reservations, native board/exit verification, safe exit checks, rollback, and persisted virtual seats exist. | Boarding and exit are another independent transaction family. A threat, command, save boundary, player exit, seat loss, or actor disappearance needs the same cancellation and reservation-release contract as all other actions. |
| Diagnostics | Per-subsystem/actor exception circuits, performance metrics, bridge health, and clipboard reports exist. | The public report summarizes counters but not the active action, prior phase transitions, last recovery, or reservation health. A generic `completion_failed` cannot be traced to its actual cause. Unrelated mod exceptions can be mistaken for Living Fellows failures. |
| Tests | Core, gameplay, UI, live-harness static, Workshop, standalone, native bridge, scavenging, vehicle, movement, and persistence gates exist. | Tests mainly prove individual successful/rejected paths. They do not yet inject cancellation and failure at every action phase, assert actor-wide ownership, or run a deterministic multi-companion reliability soak. |

### Important implementation decision

Do not rewrite the verified scavenging, medical, vehicle, or logistics commits.
Register them with the supervisor and migrate their control edges. The first
duplicate owner to remove is downtime bandage replacement: downtime should ask
Medical to own the complete treatment transaction instead of playing a second
generic visual and committing afterward.

## Scope

### Included

- actor-wide action ownership and priority;
- a canonical phase and failure vocabulary;
- safe pre-emption with rollback/release callbacks;
- progress deadlines and bounded recovery;
- the dirty-bandage duplicate-owner fix;
- navigation terminal-state recovery and target failure memory;
- integration of scavenging, logistics/equipment, vehicles, needs, work, and
  downtime with the ownership view;
- player-visible activity and wait/failure reasons;
- a contextual **What are you doing?** conversation;
- bounded public action diagnostics and a safer support bundle;
- deterministic failure injection, multi-companion soak tests, and release
  compatibility gates.

### Not included

- multiplayer or split-screen support;
- new factions, jobs, combat doctrines, dialogue systems, or base-life features;
- replacing Project Zomboid's native pathfinder;
- persisting an in-flight action across save/load;
- clearing or hijacking an unknown vanilla or third-party timed action;
- changing inventory or medical state merely to recover an animation;
- a save-schema migration unless implementation proves one is unavoidable.

Transient actions must be cancelled and reconstructed from authoritative world,
inventory, medical, and command state after load. No partial commit is saved.

## Architecture

### New module: `SCActionSupervisor`

Add `SurvivorCompanion/42/media/lua/client/SCActionSupervisor.lua`, loaded after
`SCNativeActions` and before gameplay subsystems. It is a coordinator and
read-model provider, not a second executor.

Proposed public contract:

```lua
local token, reason = SC.ActionSupervisor.begin(actor, {
    owner = "medical",
    action = "replace_dirty_bandage",
    priority = SC.ActionSupervisor.Priority.MEDICAL,
    targetKey = woundKey,
    exclusive = true,
    interruptible = true,
    deadlines = { approach = 15000, animate = 12000, commit = 1000 },
    onCancel = rollbackAndRelease,
})

SC.ActionSupervisor.transition(token, "approaching", detail)
SC.ActionSupervisor.progress(token, progressSignature)
SC.ActionSupervisor.complete(token, "bandaged", receipt)
SC.ActionSupervisor.fail(token, "no_clean_bandage", detail)
SC.ActionSupervisor.cancel(actor, "danger_preempted", minimumPriority)
SC.ActionSupervisor.snapshot(actor)
SC.ActionSupervisor.history(actor, limit)
SC.ActionSupervisor.reset(actor, "save_boundary")
```

The exact Lua shape may change during implementation, but these capabilities
and invariants may not.

### Canonical lifecycle

```text
selected
  -> reserved
  -> approaching
  -> settling
  -> animating
  -> committing
  -> verifying
  -> cooling_down
  -> completed
```

Any active phase may enter `waiting` or `recovering`. Every action ends in one
of `completed`, `cancelled`, or `failed`. Terminal records remain briefly in the
bounded history but cannot retain actor control or reservations.

Not every subsystem uses every phase. Skipped phases must be explicit in the
action definition rather than represented by fabricated work.

### Ownership invariants

1. One companion has at most one exclusive gameplay-action owner.
2. Navigation may support an action only while that owner is in `approaching`
   or an explicitly declared movement phase.
3. Locomotion cannot translate the actor during a protected interaction visual.
4. A gameplay commit runs exactly once and only after its required animation is
   verified complete.
5. Every reservation has the same owner token and is released on completion,
   cancellation, failure, reset, death, actor removal, chunk loss, and save exit.
6. Urgent survival can pre-empt lower-priority work only through the registered
   cancel callback. No subsystem may simply overwrite another owner's state.
7. An unknown vanilla or third-party timed action is treated as an external
   owner: Living Fellows waits or reports a timeout but never forcibly clears it.
8. A failed target/action pair receives a bounded retry policy. It cannot start
   again every decision tick.
9. Every terminal failure exposes a stable reason suitable for the UI, logs, and
   tests. `completion_failed` by itself is not an acceptable reason.
10. Supervisor reset never commits gameplay effects.

### Priority bands

Priority is ordered, not a license to cancel arbitrarily:

| Band | Examples | May pre-empt |
| --- | --- | --- |
| Survival emergency | escape, fire, grab/knockdown recovery, lethal threat | all interruptible lower bands |
| Immediate combat/rescue | shove, attack, urgent treatment, rescue | routine movement and work; not a synchronous commit |
| Explicit player command | retreat, regroup, direct target action, exit now | routine needs/work/downtime; transaction rollback required |
| Travel/formation/vehicle | follow, board, safe exit, guard reposition | autonomous routine work and downtime |
| Needs/medical maintenance | eat, drink, ordinary self-treatment | logistics, scavenging, work, downtime when safe to cancel |
| Productive work | scavenging, logistics, construction, crafting | downtime only |
| Downtime | read, sit, wash, ambient maintenance | nothing |

A synchronous `committing` or `verifying` phase is non-pre-emptible for its
short bounded duration. Urgent intent is queued and runs immediately afterward.

### Failure vocabulary and retry ledger

Use stable codes grouped into these categories:

- **Capability:** `api_unavailable`, `unsupported_actor_state`,
  `external_action_owned`.
- **Target:** `invalid_target`, `source_changed`, `target_unloaded`,
  `topology_changed`, `no_interaction_point`.
- **Resources:** `no_supplies`, `no_clean_bandage`, `destination_full`,
  `load_policy_rejected`, `seat_unavailable`.
- **Navigation:** `route_pending`, `route_failed`, `blocked_<type>`,
  `recovery_exhausted`.
- **Animation:** `animation_rejected`, `animation_interrupted`,
  `animation_timed_out`, `pose_not_released`.
- **Transaction:** `commit_rejected`, `verification_failed`,
  `rollback_failed`, `reservation_lost`.
- **Control:** `command_changed`, `danger_preempted`, `actor_removed`,
  `save_boundary`, `death`.

The retry key is `(actor id, action, stable target signature, failure category)`.
Suggested ordinary cooldowns are 1.5, 5, 15, then 60 seconds, capped at four
consecutive attempts. Resource absence and unchanged-container failures use
their existing longer cooldowns. A retry record resets when the command serial,
target signature, inventory capability, medical state, actor square, or world
topology changes in a way relevant to that failure.

## Work stages

### Stage 0 — Supervisor scaffold and contracts

Files:

- add `SCActionSupervisor.lua`;
- update `SCBootstrap.lua`, `SCConfig.lua`, `SCGameplayUtil.lua`,
  `SCNativeActions.lua`, `SCLocomotion.lua`, and reset paths in `SCRuntime.lua`;
- add core and gameplay fixtures.

Deliverables:

  deadlines, callbacks, retry ledger, bounded history, snapshot, and reset;
- adapters that expose existing `visual`, `needs`, `work`, and unknown native
  activities without clearing them;
- locomotion authorization reads the supervisor snapshot first and retains the
  current native-action safety fallback;
- debug assertions detect two exclusive owners, commit without verified visual,
  movement during protected pose, leaked reservation, and stale token use.

Exit gate: existing behavior remains unchanged with the compatibility adapters,
and every current harness stays green.

### Stage 1 — Medical and downtime ownership

Files:

- `SCMedical.lua`, `SCDowntime.lua`, `SCDecision.lua`, `SCDialogue.lua`, tests.

Deliverables:

- Medical owns dirty-bandage replacement from capability probe through commit;
- downtime may propose the job but cannot start a second visual or perform the
  medical commit;
- capability checks cover clean bandages and eligible emergency clothing before
  selection, with a stable `no_clean_bandage` cooldown when neither is available;
- danger and explicit orders cancel through Medical's rollback/release path;
- the actual treatment failure reason replaces `completion_failed`;
- kneel/treatment pose release is verified before locomotion is authorized.

Exit gate: no-supply, emergency-cloth, danger-at-each-phase, wound-changed,
animation-interrupted, death, and reset tests all finish with one valid medical
and inventory state and no immediate retry loop.

### Stage 2 — Scavenging and logistics integration

Files:

- `SCEncounter.lua`, `SCLogistics.lua`, `SCDecision.lua`,
  `SCGameplayUtil.lua`, tests.

Deliverables:

- preserve the 0.21.7 verified transfer contract;
- register the retained source, exact item, chosen destination, reservation,
  phase, command serial, and receipt under one supervisor token;
- logistics wear/pack/deposit/drop transactions register the same way;
- a scavenging action cannot be replaced by follow/downtime during settle or
  animation, but danger cancels before commit and releases the container;
- repeated source, capacity, route, or animation failures use the common ledger;
- successful transfer, wear, deposit, and drop invalidate the load audit and
  expose a verified terminal receipt;
- a failed destination add still rolls the exact item back to its source and
  reports rollback health separately.

Exit gate: fault injection at every phase proves no early mutation, duplication,
loss, double commit, stale reservation, or kneeling locomotion.

### Stage 3 — Navigation recovery and movement release

Files:

- `SCNavigation.lua`, `SCLocomotion.lua`, `SCPositioning.lua`,
  `SCNativeActions.lua`, tests and live harness.

Deliverables:

- associate every route with its action token and target signature;
- use native path telemetry (`hasStartedMoving`, `isMovingUsingPathFind`,
  `isTurningToObstacle`, target coordinates, cancellation state) to distinguish
  pending work from a true stall;
- on failure: wait for a legitimate native state, refresh collision/target,
  blacklist the failed edge, choose a different interaction point, then choose
  an alternate semantic target or safe fallback;
- replace the permanent same-goal `stuck_terminal` lock with a visible bounded
  failure episode. Clear it on material target/topology/command/capability change
  or an explicit timed retry; never retry every tick;
- recovery results record blocker type, failed edge, actor state, target,
  attempt, selected strategy, and outcome;
- a moving target and a static object use different invalidation rules;
- after pose completion/cancellation, require stationary/animation release
  before a new path starts; after a real escape intent, movement speed may still
  override ordinary policy.

Exit gate: doorway, corner, tree/bush, moved furniture, thumpable, vehicle,
crowd, stairs/slope, broken window, chunk boundary, unknown world collision, and
external timed-action scenarios either recover or end in one readable state.

### Stage 4 — Vehicles, weapons, and wearable equipment

## Required test matrix

### Phase fault injection

For each migrated action, inject failure before and after every applicable phase:

| Injection | Required postcondition |
| --- | --- |
| command serial changes | action cancels, reservation releases, no late commit |
| danger appears | safe rollback/cancel, then survival action owns actor |
| actor begins unknown vanilla action | Living Fellows waits and never clears it |
| target/source disappears or unloads | no mutation; bounded target failure |
| target contents/signature changes | stale task cancels; fresh selection allowed |
| navigation stalls or returns failed | alternate point/route/fallback or visible terminal episode |
| animation rejects, interrupts, or times out | no gameplay commit; pose and token release |
| destination fills after selection | source retains exact item |
| commit API rejects | unchanged state or verified rollback |
| verification fails | circuit/diagnostic opens as appropriate; no silent retry |
| actor is downed, dies, despawns, or save closes | all transient state and reservations release |

### Actor-wide invariants

The harness must assert on every scheduler tick:

- zero actors with two exclusive owners;
- zero ownerless reservations;
- zero completed tokens still controlling locomotion;
- zero commits without a verified animation when one is required;
- zero repeated commits for one token;
- zero protected-pose displacement above 0.25 tile except a declared native
  interaction transition;
- zero identical terminal failures restarted before their cooldown;
- all queued urgent actions begin after a bounded non-pre-emptible commit;
- all terminal records have a category, stable reason, actor id, action, phase,
  timestamps, and recovery outcome.

### Real-world scenarios

1. Replace a dirty bandage with a clean bandage, with emergency clothing, and
   with neither available.
2. Scavenge from a shelf, corpse, worn-bag destination, changed source, full
   destination, removed container, and a source another companion reserves.
3. Interrupt read, sit, wash, repair, craft, loot, treatment, wear, and deposit
   at approach, animation, and immediately before commit.
4. Follow through narrow doors, corners, vegetation, furniture, vehicle gaps,
   stairs, broken windows, crowds, and unloaded/loaded chunk boundaries.
5. Board more companions than seats, drive away, stop, exit, reload, and remove
   one actor while a seat transaction is pending.
6. Change weapon priority during travel and combat; equip melee, firearm,
   two-handed weapon, backpack, armor upgrade, and a conflicting wearable.
7. Save/quit during every non-commit phase and verify reconstruction from world
   truth after load.
8. Run with a deliberately failing unrelated mod fixture and verify the support
   output does not attribute its stack to Living Fellows.

## Acceptance criteria

- Every started action reaches `completed`, `cancelled`, or `failed`; no active
  action remains without progress past its phase deadline.
- Ordinary route stalls recover or become a readable bounded failure within 15
  seconds after a true stall is established. Native turns and pending path
  searches receive their documented grace period first.
- No action produces moving kneel/sit/read/loot/treatment poses.
- No verified transfer, wear, medical, work, or vehicle transaction duplicates
  or loses state under any injected failure.
- No dirty-bandage or other unchanged capability failure restarts every AI tick.
- No public status ends as unexplained `completion_failed`, `movement_rejected`,
  `unknown`, or `stuck_terminal` when a more specific cause is available.
- Unknown vanilla/third-party timed actions are never forcibly cleared.
- Ten thousand deterministic scheduler ticks at 16 actors produce zero
  invariant violations, uncaught exceptions, leaked reservations, or permanent
  stalls, while the existing performance budget remains within the 0.22.0 gate.
- The full core, gameplay, UI, live-harness static, bridge, Workshop, standalone,
  and installer test suites pass.
- A clean public playtest of at least 30 real minutes covers travel, combat,
  scavenging, treatment, equipment, vehicles, UI, save, and reload with no red
  corner errors attributable to Living Fellows.

## Release gates

1. `git diff --check` and repository static tests pass.
2. No shipped Lua uses removed mod-facing `loadstring` or `loadstream` methods.
3. Native API signature probes cover the Build 42 methods used for timed-action
   ownership, path telemetry, inventory transfer, equipment, and vehicles.
4. The mod still fails closed outside exact Build 42.20.4 and unsupported game
   modes, with a useful Support explanation.
5. A fresh save and the maintained migration save both load twice without stale
   action state or duplicate companions.
6. Public build hides destructive debug controls while retaining bounded action
   evidence and Support copy.
7. Workshop and standalone artifacts contain the same mod version and files;
   the standalone installer remains reversible and never edits
   `projectzomboid.jar`.
8. Release notes list known incompatibilities and ask testers to reproduce game
   bugs on a fresh no-mod save before reporting them upstream.

## Implementation sequence and review boundaries

Use one reviewable commit per stage. Stages 0–2 are the minimum coherent core;
do not release a build with only the supervisor scaffold. Stages 3–5 may be
tested independently after that core is green. Stage 6 changes no gameplay
semantics except defects found by its gates.

After each stage:

1. run focused core/gameplay tests for the migrated subsystem;
2. run the actor-wide invariant suite;
3. run `scripts/Test-Project.ps1`;
4. inspect the diff for a second side-effect owner or direct state clear;
5. run one protected live-sandbox scenario before starting the next stage.

If a subsystem cannot provide verified cancel/rollback semantics, it must remain
on the compatibility adapter and be reported as externally busy. It must not be
half-migrated.

- Project Zomboid 42.20.4 removed mod-facing `loadstring` and `loadstream`; a
  static shipped-Lua gate is therefore required. The official hotfix also asks
  bug reporters to reproduce game bugs on a fresh save without mods.

  `getCharacterActions`, `hasTimedActions`, `isCurrentActionPathfinding`,
  `PathFindBehavior2.cancel`, `hasStartedMoving`,

  metadata and Support output should make the bridge/install mode unambiguous.

0.22.8 is complete only when the supervisor is the single actor-wide ownership
view, every migrated subsystem ends through it, the dirty-bandage duplicate
owner is removed, navigation terminal failures are recoverable and visible,
player/support status explains current work and the last failure, all fault and
soak gates pass, and one clean public-beta playtest completes without a Living
Fellows error or permanent companion stall.
